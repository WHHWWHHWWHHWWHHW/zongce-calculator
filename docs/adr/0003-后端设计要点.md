# ADR 0003：后端 MVP 的设计要点

- 状态：已采纳；第 6–8 条负责人 2026-10-19 确认照此执行
- 日期：2026-10-13
- 关联：CLAUDE.md §6、§8 M1、§11、§13

## 决定

1. **分数精确存储、精确传输**：数据库中分数存为字符串（`DecimalText`），在 SQLite 和 MySQL 上都不会损失精度；API 中所有分数都是十进制字符串，拒绝 JSON 浮点数（422）。Excel 单元格里的数字按 `repr` 还原为最短十进制串。
2. **计分只有一份**：核算和 `/api/v1/score/preview` 都调用 `zongce_engine`；规则版本（规则 JSON + 能力分目录）完整存进数据库，并按 sha256 去重，同一版本号内容不同时拒绝导入。
3. **能力分 = 已通过申报之和**：按目录中的封顶分组（文学作品 5、参与分 1、公益附加 5、宿舍 10）汇总后交给引擎，引擎再按 0–50 封顶。目录 `rules/ability-catalog-xxgc-2020.json` 逐条转录自细则附件 2，每项都注明出处；原文需要酌情或另行判断的一律人工给分。
4. **建议分 ≠ 得分**：目录只算建议分（多人项目按 (N−M+1)/(1+…+N) 分配，兼职按 1、1/2、1/4、1/8），按正文第六条四舍五入保留 4 位；最终得分由审核人确认，改分与驳回必须填写理由。
5. **审计**：审核、学院成绩数据变更（导入或手改）、核算导致的综测成绩变化、学年状态、账号变更、公示、异议处理都写审计日志（谁、何时、改前、改后、理由）。日志不记录密码。
6. **API 层不做会改变结果的范围校验**（CLAUDE.md §13 第 6 项未定）：GPA、体测等只要求是有限十进制数，与 legacy 一致。
7. **同分并列排名**（1、2、2、4），组内再按学号排序展示。办法没有规定并列怎么处理。
8. **不能审核自己的申报**；班级审核员只能审核本班；已通过的申报只有学院管理员可以改分。
9. **账号**：管理员批量导入，随机初始密码（去掉易混淆字符）只在导入响应中返回一次；首次登录必须改密码，改密码、重置密码、停用账号都会使旧令牌失效（`token_version`）。
10. **材料上传**：按文件头识别 PDF / PNG / JPEG，不信任客户端声明的类型；限制大小和数量；以随机名存储，不使用用户提供的文件名拼接路径。
11. **数据库兼容**：开发和测试用 SQLite，迁移同时在 MySQL 8 上验证（CI）；枚举用 VARCHAR + CHECK 约束，不用数据库原生 ENUM。

## 后果

- 前端（M2）的类型从 `docs/api/openapi.json` 生成；测试保证这个文件与代码一致。
- 第 6–8 条以后如需调整，改动范围很小：在 schema 中加取值范围、在 ranking 中改并列规则、在 review 中放宽限制。
